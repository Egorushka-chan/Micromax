# AGENTS.md

## Контекст проекта

Этот репозиторий содержит дипломный проект MicroMax — информационную систему управления микроскладом.

Система не является полноценной ERP, заменой 1С или копией МойСклад. Проект ориентирован на узкий сценарий микросклада: простое адресное хранение, быстрые складские операции, мобильный сценарий работы, низкий порог входа, а также дальнейшее развитие через шаблоны быстрого запуска и командный интерфейс.

Основные сущности предметной области:

- склад;
- зона хранения;
- ячейка хранения;
- товар / номенклатура;
- остаток;
- складская операция;
- пользователь;
- роль;
- журнал операций.

Основные складские операции:

- приёмка товара;
- размещение товара в ячейке;
- перемещение товара между ячейками;
- списание / расход товара;
- просмотр местонахождения товара;
- просмотр содержимого ячейки;
- просмотр истории операций.

Важные особенности продукта:

- мобильное Android-приложение является основным пользовательским интерфейсом;
- серверная часть содержит основную бизнес-логику;
- мобильное приложение взаимодействует с сервером через REST API;
- PostgreSQL используется как основная серверная база данных;
- SQLite используется на мобильной стороне для кэша, настроек и потенциального оффлайн-режима;
- QR-коды являются вспомогательной функцией, а не центральной идеей проекта;
- командный помощник на естественном языке является нужной функцией;
- все операции изменения данных через командный интерфейс должны требовать подтверждения пользователя.

## Общие правила работы

Перед внесением изменений необходимо изучить соответствующие файлы и сохранить существующую концепцию проекта.

Нельзя самовольно менять масштаб проекта. Не следует добавлять ERP, CRM, бухгалтерию, налоговый учёт, продажи, фискальную регуляторику или сложные корпоративные функции, если это явно не требуется задачей.
Для большего понимания проекта можешь прочитать файл `Концепция микросклада и сравнение конкурентов.docx`

Предпочтительны небольшие и точечные изменения. При реализации функциональности нужно учитывать рамки MVP.

При изменении кода необходимо:

- кратко объяснить, что было изменено;
- перечислить затронутые файлы;
- указать, как проверить результат;
- не добавлять новые production-зависимости без явной причины;
- не удалять существующий код и файлы без прямого требования;
- добавлять краткий комментарий (к классам; в места, где возможны проблемы с понимаем кода).

При работе с документами необходимо:

- писать на русском языке;
- иметь ввиду, что написаное будет поверятся в системе Антиплагиат, что включает в себя проверку на ИИ. Обязательно учитывать это, и писать не в стиле ИИ.
- использовать формальный стиль, подходящий для дипломной работы и пояснительной записки;
- избегать рекламных формулировок;
- использовать точные академические формулировки;
- сохранять терминологическую согласованность.

Предпочтительные термины:

- складская структура;
- зона хранения;
- ячейка хранения;

## Принятые технические решения

Мобильный клиент:

- Android;
- Kotlin;
- Jetpack Compose;
- Android Studio;
- SQLite
- пространство имён приложения: `com.bezborodov.micromax`.

Серверная часть:

- ASP.NET Core;
- REST API;
- серверная проверка складских операций;
- сервер является основным источником истины для изменения остатков.

Базы данных:

- PostgreSQL на серверной стороне;
- SQLite на мобильной стороне для локального кэша, настроек, частичной функциональности оффлайн и потенциальной очереди оффлайн-операций.

Архитектура:

- клиент-серверная архитектура;
- мобильное приложение отправляет запросы на сервер;
- сервер проверяет права пользователя и корректность операции;
- изменение остатков должно выполняться транзакционно;
- каждая успешная операция, изменяющая остатки, должна создавать запись в журнале операций.

## Правила предметной области

Мобильное приложение не должно изменять остатки как произвольные числовые значения. Остатки должны изменяться только через складские операции.

Для операций изменения остатков необходимо проверять:

- авторизацию пользователя;
- права пользователя;
- существование товара;
- существование исходной ячейки, если она требуется;
- существование целевой ячейки, если она требуется;
- положительное количество;
- достаточность остатка для списания и перемещения.

Для операции перемещения необходимо:

- уменьшить остаток в исходной ячейке;
- увеличить остаток в целевой ячейке;
- создать запись в журнале операций;
- выполнить все действия атомарно.

Для операции списания необходимо:

- уменьшить остаток в выбранной ячейке;
- создать запись в журнале операций;
- отклонить операцию, если количество превышает доступный остаток.

Для приёмки и размещения необходимо:

- увеличить остаток в целевой ячейке;
- создать запись в журнале операций.

## Текущее состояние разработки

Проект находится на стадии MVP-прототипа. Реализованы базовые серверные API, демо-данные, мобильный клиент на Android и начальная интеграция мобильного приложения с сервером.

Мобильное приложение уже содержит:

- главный экран с карточкой статистики;
- нижнюю навигацию;
- экран номенклатуры;
- экран ячеек хранения;
- экран складских операций;
- экран командного помощника;
- экран настроек;
- загрузку данных с серверной части;
- отображение состояний загрузки, ошибок и пустых списков;
- формы операций с выбором товара и ячеек из загруженных данных;
- экран подтверждения перед выполнением операций изменения остатков;
- ViewModel для загрузки данных, операций и команд ассистента.

Серверная часть уже содержит:

- REST API для складов, зон, ячеек, товаров, остатков, операций, пользователей и ролей;
- сервис выполнения складских операций;
- серверную проверку операций изменения остатков;
- транзакционное изменение остатков;
- создание записей в журнале операций;
- начальную обработку команд ассистента;
- демо-данные для проверки MVP.

# Командный интерфейс MicroMax

## Назначение командного интерфейса

Командный интерфейс в системе MicroMax предназначен для быстрого выполнения типовых действий микросклада через текстовый запрос пользователя. Он не заменяет основные экраны мобильного приложения, а дополняет их: пользователь может найти товар, получить сводку по остаткам, подготовить складскую операцию или перейти к нужному разделу без ручного поиска по меню.

Ключевое ограничение интерфейса состоит в том, что помощник не изменяет данные напрямую. Любая команда, которая может повлиять на номенклатуру или остатки, сначала преобразуется в структурированное намерение, затем проверяется сервером и только после подтверждения пользователя передаётся в существующие складские сервисы.

## Общая схема работы

Пользователь вводит команду в мобильном приложении. Мобильный клиент отправляет текст на серверный endpoint `/api/assistant/interpret`. Сервер формирует минимальный контекст для ИИ: список товаров, список ячеек хранения и перечень доступных команд. После этого команда передаётся одному из провайдеров ИИ.

Провайдеры подключаются по цепочке:

1. локальная модель Ollama;
2. OpenAI;
3. Mock-провайдер.

Основной режим рассчитан на локальную Ollama с моделью `qwen3-vl:8b`. Если локальная модель недоступна, сервер пробует OpenAI. Если и OpenAI недоступен или не настроен, используется Mock-провайдер. Mock-провайдер не требует внешних сервисов и позволяет сохранить работоспособность MVP.

Если система временно перешла на Mock-провайдер, это не считается постоянным режимом. Фоновый сервис периодически проверяет, восстановились ли Ollama или OpenAI. Когда реальный провайдер снова становится доступным, следующие команды могут быть обработаны через него.

## Централизованный реестр команд

Список доступных команд хранится централизованно в серверном реестре `AiCommandRegistry`. Такой подход нужен для того, чтобы не поддерживать несколько независимых списков команд в prompt, mock-логике, валидации и API.

Для каждой команды в реестре указываются:

- системное имя команды;
- пользовательское название;
- описание;
- уровень риска;
- необходимость товара;
- необходимость исходной ячейки;
- необходимость целевой ячейки;
- необходимость количества;
- признак исполняемой команды;
- примеры пользовательских формулировок;
- фразы, по которым Mock-провайдер может распознать команду.

Реестр используется в нескольких местах:

- при формировании prompt для реальной ИИ-модели;
- при rule-based распознавании в Mock-провайдере;
- при серверной нормализации и проверке команды;
- при выдаче списка команд через `/api/assistant/commands`.

Благодаря этому добавление новой команды должно начинаться с изменения реестра. Остальные части системы получают описание команды из одного источника.

## Уровни риска

Команды делятся по уровню риска:

- `None` — безопасные команды просмотра и навигации;
- `Low` — действия, которые подготавливают результат, но не меняют остатки;
- `Medium` — изменение справочных данных, например создание товара или изменение минимального остатка;
- `High` — операции, изменяющие остатки;
- `Critical` — зарезервированный уровень для потенциально особо опасных действий.

Команды уровня `Medium`, `High` и `Critical` требуют подтверждения пользователя. Это правило применяется на сервере и не зависит от того, какой провайдер ИИ распознал команду.

## Работа с неоднозначными запросами

Если пользовательский запрос нельзя однозначно интерпретировать, система не должна угадывать. Например, если в справочнике есть несколько похожих товаров, помощник должен задать уточняющий вопрос и предложить варианты.

Для этого ответ провайдера может иметь режим:

- `Command` — команда распознана и содержит необходимые параметры;
- `Clarification` — требуется уточнение;
- `Unknown` — команда не распознана.

В режиме `Clarification` сервер возвращает вопрос и список вариантов. Например, пользователь может написать «найди перчатки», а в справочнике будут «Перчатки рабочие» и «Перчатки утеплённые». В этом случае система должна попросить выбрать конкретную позицию.

Даже если реальная ИИ-модель вернула команду как однозначную, сервер дополнительно проверяет, существуют ли указанные товар и ячейки. Если данные не проходят проверку, команда преобразуется в уточняющий ответ.

## Провайдеры ИИ

Реальные провайдеры подключаются через `Microsoft.Extensions.AI` и общий интерфейс `IChatClient`. Это позволяет не привязывать бизнес-логику к конкретному поставщику модели.

Ollama используется как локальный провайдер. Он удобен для дипломного проекта, потому что может работать на компьютере разработчика без обращения к внешним сервисам. OpenAI используется как резервный внешний провайдер, если локальная модель недоступна. Mock-провайдер является последним fallback и реализует простые правила распознавания.

Выбор провайдера выполняет `AiProviderSelector`. Он проходит по цепочке провайдеров и использует первый доступный вариант. Если реальный провайдер вернул ошибку или невалидный ответ, он временно помечается как недоступный, а запрос передаётся следующему провайдеру.

За восстановление отвечает `AiProviderRecoveryService`. Он периодически проверяет недоступные реальные провайдеры и возвращает их в работу после успешной проверки.

## Формирование prompt

Prompt формируется сервером в `AiCommandPromptBuilder`. В него включается только необходимый контекст:

- список товаров с идентификатором, названием и SKU;
- список ячеек с идентификатором, кодом и названием;
- описание доступных команд из централизованного реестра;
- правила выбора режима `Command`, `Clarification` или `Unknown`;
- требование вернуть только JSON.

Модель должна вернуть структурированный ответ. В ответе указываются тип команды, уровень риска, идентификаторы товара и ячеек, количество, краткое описание, уточняющий вопрос и варианты выбора, если они нужны.

Сервер не доверяет ответу модели полностью. После получения JSON выполняется нормализация типа команды, проверка уровня риска, проверка обязательных параметров и сверка идентификаторов с базой данных.

## Выполнение команд

После интерпретации сервер возвращает команду мобильному приложению. Если команда безопасная, результат может быть показан сразу. Если команда требует подтверждения, она сохраняется в списке ожидающих команд и получает `commandId`.

Для подтверждения мобильное приложение вызывает `/api/assistant/confirm`. Сервер извлекает ожидающую команду и выполняет её через существующую бизнес-логику:

- поступление выполняется через `WarehouseOperationService.ReceiveAsync`;
- перемещение выполняется через `WarehouseOperationService.MoveAsync`;
- списание выполняется через `WarehouseOperationService.WriteOffAsync`;
- создание товара и изменение минимального остатка выполняются через серверную работу с БД.

Операции изменения остатков проходят через существующий сервис складских операций. Это важно, потому что именно он выполняет проверки количества, существования ячеек, достаточности остатка, транзакционное изменение данных и создание записей журнала операций.

## Роль мобильного приложения

Мобильное приложение отображает overlay командного помощника поверх текущего экрана. Пользователь видит историю сообщений, поле ввода, быстрые подсказки, карточку результата и карточку подтверждения.

Клиентская часть не должна самостоятельно выполнять опасные операции. Её задача — отправить текст команды на сервер, показать ответ, получить подтверждение пользователя и отправить подтверждение обратно на сервер.

Список команд запрашивается с сервера через `/api/assistant/commands`. Быстрые подсказки в overlay формируются на основе серверного реестра команд. Это исключает необходимость поддерживать отдельный список команд в мобильном приложении.

## Безопасность

Командный интерфейс построен так, чтобы ИИ не был источником истины. Модель только помогает преобразовать естественный язык в структурированную команду. Все критичные решения остаются на сервере:

- проверка существования товара;
- проверка существования ячеек;
- проверка положительного количества;
- проверка достаточного остатка;
- определение необходимости подтверждения;
- выполнение операций через транзакционную бизнес-логику.

Такой подход снижает риск ошибочного выполнения команды и соответствует предметной области микросклада, где изменение остатков должно быть контролируемым и прослеживаемым.

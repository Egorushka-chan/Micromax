# Mobile/AGENTS.md

## Контекст мобильного приложения

В этой папке находится Android-приложение MicroMax.

Используемый стек:

- Kotlin;
- Jetpack Compose;
- Android Studio.

Пространство имён приложения:

`com.bezborodov.micromax`

Мобильное приложение является основным пользовательским интерфейсом системы. Оно должно быть ориентировано на быстрые складские действия: просмотр товаров, просмотр ячеек, проверку остатков, выполнение операций и просмотр журнала действий.

## Принципы интерфейса

Интерфейс должен быть простым и практичным, без избыточной декоративности.

Основные экраны должны быть организованы вокруг предметной области:

- склады;
- зоны;
- ячейки;
- товары;
- остатки;
- складские операции;
- журнал операций.

Важные пользовательские сценарии:

- найти, где хранится товар;
- узнать, сколько товара осталось;
- открыть ячейку и посмотреть её содержимое;
- принять товар в ячейку;
- переместить товар между ячейками;
- списать товар из ячейки;
- посмотреть последние операции.

Не следует усложнять интерфейс лишними переходами. Предпочтительны понятные карточки, списки, формы и диалоги подтверждения.

## Правила Jetpack Compose

Использовать подходы, характерные для Jetpack Compose:

- экраны в виде composable-функций;
- вынос состояния выше по иерархии, где это уместно;
- ViewModel для состояния экранов;
- неизменяемые модели состояния UI, где это возможно;
- Preview для важных composable-компонентов, если это практично.

Не размещать бизнес-логику напрямую внутри composable-функций. Composable должны отображать состояние и вызывать callback-функции.

## Ожидаемая архитектура мобильного приложения

Предпочтительная структура:

- `ui/` — экраны, компоненты, навигация;
- `viewmodel/` — ViewModel или ViewModel для конкретных экранов;
- `domain/` — доменные модели и use case;
- `data/` — репозитории, источники данных;
- `network/` — DTO и код взаимодействия с REST API;
- `local/` — SQLite, кэш, локальные настройки, очередь оффлайн-операций.

Сервер является основным источником истины для складских операций. Мобильное приложение может кэшировать данные, но операции изменения остатков должны синхронизироваться с сервером.

## Безопасность операций изменения данных

Любая операция, изменяющая остатки, должна иметь понятный этап подтверждения в интерфейсе.

Перед отправкой операции пользователь должен видеть:

- тип операции;
- товар;
- количество;
- исходную ячейку, если применимо;
- целевую ячейку, если применимо.

После выполнения операции необходимо показать результат: успешное выполнение или понятное сообщение об ошибке.

## Правила разработки

Не добавлять новые зависимости без необходимости.

При добавлении экранов сохранять понятную и последовательную навигацию.

Если используются тестовые данные, они должны быть явно обозначены как mock/sample data.

Не хранить в коде реальные логины, пароли, токены, серверные секреты или приватные URL.

Если серверная часть ещё не реализована, использовать интерфейсы репозиториев и mock-реализации, чтобы позже можно было заменить их на реальные REST API-источники.
